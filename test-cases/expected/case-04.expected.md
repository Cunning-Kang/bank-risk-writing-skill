# Case 04 Expected: formal-polish-basic

## 期望输出结构

输出必须严格包含以下段落（对应 `formal-polish.md` 的 `Default Output Structure`）：

1. **修改方向** — 用 3–5 条说明本次润色做了什么；只描述语言和结构调整，不声称新增分析
2. **修订稿** — 完整改写后的正文；以连贯文本呈现，**不得夹杂解释性括注**
3. **待核实事项**（如有）— 仅在满足 §3 触发条件时出现；若无则可省略

### 待核实事项适用条件

本节仅在原文存在以下任一情况时列出：
- 具体数字、日期、机构、文件名称未见来源
- 原文存在"明显强结论"但支撑不足
- 涉及政策依据、监管要求、实施口径但原文未交代出处
- 时间范围、适用对象、责任主体表述不清

## 期望出现的关键特征

### 结构性检查

| 检查项 | 标准 |
|--------|------|
| 修改方向条目数 | 3–5 条 |
| 修订稿完整性 | 覆盖原文所有实质性段落，无遗漏 |
| 待核实事项（如触发） | 逐条列出，每条说明待核实内容与原因 |

### 表达与风格

- 修改方向具体说明了改写类型（如口语化→书面化、绝对化→审慎化、冗余→简洁等），而非泛泛一句"提升表达"
- 修订稿为正式、审慎、结构清晰的书面文本
- 原文所有关键信息被保留，未被空泛表述替代
- 未出现原文不包含的事实、数字或出处

### 边界标注

- 如原文含无来源数字或无依据强结论，待核实事项中逐条标出
- 如原文事实充分、无需核实，可省略待核实事项节（本 case 无强制要求）

## 不应出现的问题

### Hard Rules 映射（对应 formal-polish.md Hard Rules）

- 新增原文中未提及的事实、数字、出处、案例、机构判断
- 擅自把"可能、或许、初步、倾向于"改成确定结论
- 为显得专业而堆砌术语或长句
- 把普通工作文字改写成宣传稿、新闻稿、评论稿
- 用空话替代原文信息（如用"持续推进相关工作"替换原文的具体行动描述）
- 原文信息不足时，脑补补齐而非保留边界或提示核实

### 高风险错误触发条件（对应 TEST_PLAN.md §六）

| 高风险错误 | 本 case 触发条件 |
|------------|------------------|
| 编造事实 | 修订稿中出现原文不含的具体数字、日期、机构名 |
| 编造政策口径 | 修订稿中模拟了原文未提及的监管要求或内部标准 |
| 越界推断 | 把原文的推测性或倾向性判断改写为确定结论 |
| 风格严重偏离 | 修订稿呈现明显新闻稿、营销稿或口语化风格 |
| 空泛建议 | 用"加强重视""持续推进"等替代原文原有具体内容 |
| 漏标不确定性 | 原文含明显待核实内容但输出中无任何标注 |

## 验收口径

| 条件 | 判定 | 判定方式 |
|------|------|----------|
| 修改方向为 3–5 条 | 必须通过 | 计数 |
| 修订稿无解释性括注 | 必须通过 | 搜索 `（…）` 或 `(…)` 内非引述内容 |
| 原意未改变 | 必须通过 | 逐段比对原文与修订稿，关键信息无遗漏或转义 |
| 未新增事实/数字/出处 | 必须通过 | 修订稿中无原文不含的具体事实 |
| 风格正式审慎 | 必须通过 | 无口语化、情绪化、营销化表述 |
| 不堆砌术语长句 | 建议通过 | 无明显为提升"专业感"而生造的冗长表达 |
| 待核实事项逐条具体（如触发） | 建议通过 | 每条说明待核实内容与原因 |

### 判定总结

- 所有"必须通过"项均通过 → 该 case 通过
- 任一"必须通过"项不通过 → 该 case 不通过
- "建议通过"项不通过不直接导致不通过，但应在评审记录中标注
